> หรือใช้ `?view=workspace|list|detail&state=<state>`)
> Screenshot ภาษาไทยอยู่ใน `mockups/proposals/956-screens/` ใช้ชื่อไฟล์ `<view>-<state>-<width>.png`

ขอบเขตยึดตาม issue #956 เท่านั้น: ไม่มี SLA, ประเภทเคส, เลขเคส `CS-xxxx`, router, มุมมอง Supervisor/Admin,
task/attachment และการสร้างเคสจาก Console

## 1. ผู้ใช้และงานที่ต้องสำเร็จ

ผู้ใช้คือ **เอเจนต์** ตามตารางใน `docs/ui-principles.md` ใช้สองแอป ใน `apps/workspace` เอเจนต์ยังอยู่ในสายหรือกำลังสรุปผล
ต้องเปิดเคสได้ภายในไม่กี่วินาทีโดยไม่บังปุ่มควบคุมสายและไม่ทำให้หน้าทำงาน remount ใน `apps/console` เอเจนต์กลับมาติดตามเคส
ของตัวเองและของทีมหลังจบงาน เขียนโน้ต ส่งต่อให้เพื่อนในทีม และปิดเรื่องเมื่อจบ การปิดเคสย้อนกลับไม่ได้
จึงต้องยืนยันก่อนตามหลักการข้อ 5 ส่วน Supervisor/Admin ยังไม่มีมุมมองของตัวเองในรอบนี้

## 2. User flow

### 2.1 เปิดเคสจาก Workspace

1. งานอยู่ใน `ACTIVE` หรือ `WRAPUP` ปุ่ม **เปิดเคส** แสดงอยู่ในแถบบริบทของงาน (ขวาของชื่อผู้โทรและรหัสงาน)
   ตอน `ASSIGNED` (สายยังไม่รับ) และตอนไม่มีงาน ไม่แสดงปุ่ม
2. กดปุ่มแล้วแผงงานด้านขวาเปิด (ถ้าปิดอยู่) และเลือกแท็บ **เคส** focus ไปที่ช่อง "หัวข้อ"
   เป็น panel แบบ non-modal ไม่ใช้ `Dialog` เพราะหลักการข้อ 4 ห้าม modal ที่ขวางการคุย ปุ่มควบคุมสายยังกดได้ตลอด
3. ฟอร์มแสดงลูกค้าที่ผูกกับงานและงานที่จะผูก (อ่านอย่างเดียว) ตามด้วยหัวข้อ (จำเป็น), โน้ตแรก (จำเป็น)
   และผู้รับผิดชอบ (ค่าเริ่มต้นคือตัวเอง)
4. กด **เปิดเคส** ระบบส่งคำสั่งพร้อม `commandId` ระหว่างรอ ปุ่มเป็น "กำลังเปิดเคส…" และฟิลด์ทั้งหมดเป็น read-only
5. สำเร็จ: แท็บเคสแสดง "เปิดเคสแล้ว" พร้อมหัวข้อ สถานะ ผู้รับผิดชอบ ลูกค้า และลิงก์ **เปิดเคสใน Console (แท็บใหม่)**
   ลิงก์สร้างแบบเดียวกับ `historyHref` (`apps/workspace/src/workspace-app.tsx` ราว 1450-1468):
   `VITE_CONSOLE_URL` + `?view=team-cases&case=<caseId>&tenant=<alias>` แสดง toast "เปิดเคสแล้ว" หนึ่งครั้ง
   ด้านล่างมีปุ่ม ghost **เปิดเคสอีกเรื่องจากงานนี้** สำหรับคืนฟอร์มเปล่าและสร้าง `commandId` ใหม่

Path ที่ล้มเหลวและการย้อนกลับ:

| เหตุ | สิ่งที่ผู้ใช้เห็น | ทางออก |
| --- | --- | --- |
| งานยังไม่ผูกลูกค้า (unlinked) | แถบเตือน "เลือกลูกค้าให้งานนี้ก่อน" พร้อมปุ่ม **ไปเลือกลูกค้า** ส่วนลูกค้าในสรุปเป็น "ยังไม่ได้เลือก" กรอกร่างได้ แต่ปุ่มเปิดเคสใช้ไม่ได้ (`aria-describedby` ชี้ไปที่แถบเตือน) | ปุ่ม **ไปเลือกลูกค้า** สลับแท็บหลักเป็น Customer 360 และ focus ช่องค้นหา เมื่อผูกลูกค้าแล้ว สรุปในฟอร์มอัปเดตเองและปุ่มกดได้ ร่างยังอยู่ |
| ไม่ทราบผล (timeout/เครือข่าย) | แถบ "ยังไม่ทราบผลการเปิดเคส…" ฟิลด์ถูกล็อก ปุ่มหลักเป็น **ส่งคำสั่งเดิมอีกครั้ง** | ส่ง `commandId` เดิมพร้อม payload เดิม ระบบไม่สร้างเคสซ้ำ (แบบเดียวกับ wrapup `unknown`) |
| ผู้รับผิดชอบถูกปฏิเสธ (ไม่ active, ย้ายทีม) | error ใต้ช่องผู้รับผิดชอบ "ผู้รับผิดชอบนี้ไม่อยู่ในทีมหรือไม่ active แล้ว เลือกใหม่" | โหลดรายชื่อทีมใหม่ เลือกใหม่แล้วส่ง ด้วย `commandId` ใหม่ |
| ข้อมูลไม่ผ่าน (หัวข้อหรือโน้ตว่าง, ยาวเกิน) | error ใต้ฟิลด์ที่ผิด, ปุ่มยังกดได้ แต่กดแล้ว focus ไปที่ฟิลด์แรกที่ผิด | แก้ฟิลด์ |
| บัญชีไม่อยู่ในทีม | แท็บเคสแสดงแถบ "บัญชีของคุณยังไม่อยู่ในทีม จึงเปิดเคสไม่ได้ ติดต่อผู้ดูแล tenant" ไม่มีฟอร์ม | ติดต่อ admin, งานและสายทำต่อได้ |
| Session หมดอายุ | ใช้ flow reauthenticate เดิมของ Workspace, ร่างยังอยู่ | ยืนยันตัวตนแล้วส่งใหม่ |
| งานเปลี่ยน `ACTIVE → WRAPUP` ระหว่างกรอก | ไม่ remount ร่างยังอยู่ | ส่งได้ตามปกติ |
| บันทึกผล (wrapup) ไปก่อนส่งเคส | แท็บเคสเหลือร่างแบบอ่านอย่างเดียว พร้อมข้อความ "บันทึกผลงานนี้แล้ว จึงเปิดเคสจากงานนี้ไม่ได้" | ดูข้อ 8 คำถาม 3 |

ทางลัดใน wrapup: เมื่อเลือกผล **ต้องติดตามต่อ** และงานนี้ยังไม่มีเคสที่เปิดใน session นี้ แท็บ "สรุปผล" แสดงแถบข้อมูล
"ต้องติดตามต่อ? เปิดเคสก่อนบันทึกผล…" พร้อมปุ่ม **ไปที่แท็บเคส** (`workspace-wrapup-hint-1280.png`) ไม่บังคับ
และไม่ขวางปุ่มบันทึกผล

ร่างเก็บใน state ต่อ `workId` เท่านั้น ไม่เขียน localStorage เพราะมี PII ของลูกค้า การปิดแท็บเคสหรือสลับแท็บไม่ทำให้ร่างหาย
**ล้างร่าง** ล้างทันทีโดยไม่ต้องยืนยัน เพราะเนื้อหายังไม่ถูกบันทึก ถ้าทำผิดก็พิมพ์ใหม่ได้

### 2.2 เคสของทีม (Console รายการ)

1. เข้าจาก rail area `cases` → SubNav **เคสของทีม** (`?view=team-cases`) หรือจากลิงก์ใน Workspace
2. ค่าเริ่มต้นของ filter: สถานะ "ยังไม่ปิด" และผู้รับผิดชอบ "ของฉัน" (ข้อ 8 คำถาม 4) ค่า filter อยู่ใน URL
   (`status`, `assignee=me|team`) ไม่มี PII เรียงตามอัปเดตล่าสุดใหม่ไปเก่าเสมอ
3. กดหัวข้อหรือปุ่ม **เปิด** ท้ายแถวเพื่อไปที่รายละเอียด (`?view=team-cases&case=<id>`, `pushState` เพื่อให้ปุ่ม Back ของเบราว์เซอร์กลับมาที่ filter เดิม)
4. Error/401/403 ตามตาราง state ในหัวข้อ 4

### 2.3 รายละเอียดเคส (Console)

1. โหลดเคส + ไทม์ไลน์ (และข้อมูลลูกค้าแยกกัน เพื่อให้แสดงผลบางส่วนได้)
2. Action ตามสถานะ:
   - `OPEN`: **มอบหมาย**, **ทำเครื่องหมายว่าแก้แล้ว** (ปุ่มหลัก)
   - `RESOLVED`: **มอบหมาย**, **เปิดเคสอีกครั้ง**, **ปิดเคส** (ปุ่มหลัก)
   - `CLOSED`: ไม่มี action แสดงแถบ "เคสนี้ปิดแล้วเมื่อ … อ่านได้อย่างเดียว" แทนช่องเพิ่มโน้ต
3. เพิ่มโน้ต: พิมพ์ในช่องท้ายไทม์ไลน์ → **บันทึกโน้ต** → โน้ตต่อท้ายไทม์ไลน์ ช่องว่างลง และ toast "บันทึกโน้ตแล้ว"
4. มอบหมาย: `Dialog` เลือก Agent ที่ active ในทีม → **มอบหมาย** → ปิด dialog, toast "มอบหมายให้ {name} แล้ว",
   ไทม์ไลน์เพิ่มรายการ `ASSIGNED`
5. แก้แล้ว/เปิดอีกครั้ง: เปลี่ยนสถานะทันทีโดยไม่ยืนยัน เพราะย้อนกลับได้ แล้วแสดง toast
6. ปิดเคส: `Dialog` แบบ `role="alertdialog"` ที่ระบุชื่อเคส → **ปิดเคส** (danger) → หน้าเป็นอ่านอย่างเดียว พร้อม toast
7. Conflict (`expectedVersion` ไม่ตรง): แถบเตือนใต้หัวเคส "เคสนี้ถูกแก้ไขหลังจากคุณเปิดหน้า…" ปุ่ม **โหลดเคสล่าสุด**
   ร่างโน้ตยังอยู่ action อื่นถูกปิดไว้จนกว่าจะโหลดใหม่ ถ้า conflict เกิดใน dialog ให้ปิด dialog แล้ว focus ไปที่แถบเตือน
   หลังโหลดใหม่ ถ้าเคสกลายเป็น `CLOSED` ร่างโน้ตจะแสดงแบบอ่านอย่างเดียวพร้อมปุ่ม "คัดลอกร่าง" เพื่อไม่ให้ข้อความหาย
8. ไม่ทราบผล (timeout): ปุ่มที่กดค้าง "กำลังบันทึก…" แล้วเปลี่ยนเป็น "ยังไม่ทราบผล ส่งคำสั่งเดิมอีกครั้ง" ใช้ `commandId` เดิม

## 3. โครงหน้าจอและ component

ใช้ `@d-contact/ui-react` ทั้งหมดตามตารางด้านล่าง component ใหม่ทุกตัวเป็น local ของแอป ยังไม่ควรเข้า `ui-react`
เพราะมีผู้ใช้เพียงที่เดียว

### 3.1 Workspace (แท็บ "เคส" ในแผงงาน)

| ส่วน | Component | หมายเหตุ |
| --- | --- | --- |
| ปุ่มเปิดเคสในแถบบริบท (`aw-v3-context`) | `Button` variant `secondary` size `md` | วางขวาสุดของแถบเดียวกับชื่อผู้โทร |
| แท็บ "เคส" | `Tab`/`TabPanel` ใน `Tabs` เดิมของ inspector | ลำดับ: สรุปผล, **เคส**, รายละเอียด, เหตุการณ์, ความพร้อม ใช้ `shouldForceMount` เพื่อไม่ให้ร่างหาย |
| สรุปลูกค้าและงานที่ผูก | `<dl>` ในแอป | อ่านอย่างเดียว, พื้น `--dc-surface-sunken`, ขอบ `--dc-border-subtle` |
| หัวข้อ | `TextField` (`isRequired`, `maxLength` 200, `description`, `errorMessage`) | ตัวนับ "n / 200" อยู่ใน `description` |
| โน้ตแรก | `TextField multiline` | 1–2,000 ตัวอักษร ใช้กฎ normalize เดียวกับ wrapup note |
| ผู้รับผิดชอบ | `Select` | ตัวเลือกแรก "ตัวฉัน ({name})" ตามด้วย Agent ที่ active ในทีม เรียงตามชื่อ |
| แถบ unlinked/unknown/no team | แถบข้อความในแอป (`role="status"`) | สี attention/info จาก token ไม่ใช้สีอย่างเดียว มีไอคอนและข้อความ |
| ปุ่มเปิดเคส/ล้างร่าง | `Button` `primary` + `ghost` | อยู่ในแถบ sticky ท้ายแผง เพื่อให้มองเห็นที่ 1280×800 โดยไม่ต้องเลื่อน |
| สถานะเคสหลังสร้าง | `StatusChip` (ดู mapping 3.4) | |
| Toast | `toastQueue.add({ tone: 'success' })` | |

### 3.2 Console: เคสของทีม

ยึด `mockups/history.html` (Interactions): หัวหน้า → การ์ด filter เหนือตาราง → ตาราง → แถบท้ายตารางที่มีจำนวนและปุ่มเปลี่ยนหน้า

| ส่วน | Component |
| --- | --- |
| หัวหน้า (h1 "เคสของทีม" + ชื่อทีม) และปุ่มรีเฟรช | `Button` secondary |
| Filter สถานะ, ผู้รับผิดชอบ | `Select` × 2 (label อยู่เหนือ control) และ `Button ghost` "ล้างตัวกรอง" แสดงเมื่อค่าไม่ใช่ค่าเริ่มต้น |
| ตาราง | `Table`, `TableHeader`, `Column` (`isRowHeader` ที่หัวข้อ), `TableBody`, `Row`, `Cell`; หัวตารางติดบน, แถวสูง `--dc-row-table` |
| สถานะ | `StatusChip` |
| เครื่องหมาย "คุณ" ข้างชื่อผู้รับผิดชอบ | `Badge tone="neutral"` |
| action ท้ายแถว | `Button size="sm"` "เปิด" + `aria-label` "เปิดเคส {title}" |
| ท้ายตาราง | ข้อความจำนวน + `Button ghost` ก่อนหน้า/ถัดไป (cursor) |
| Skeleton | local `CaseListSkeleton` ในแอป (ui-react ยังไม่มี skeleton) 8 แถวสูงเท่าแถวจริง |

คอลัมน์และความกว้างที่ 1280: หัวข้อ 34% (ตัด 1 บรรทัด + `title` แสดงเต็ม), ลูกค้า 17% (ตัด), สถานะ 104px,
ผู้รับผิดชอบ 17% (ตัด), อัปเดตล่าสุด 150px (`dateStyle: 'medium', timeStyle: 'short'`), งานที่ผูก 84px ชิดขวา, action 64px
ไม่มีช่องค้นหา เพราะ API รอบนี้ไม่มี (ข้อ 8 คำถาม 7)

**ต่างจากหน้าอ้างอิง**: ไม่มี Export, ไม่มีช่วงวันที่ และท้ายตารางไม่แสดงจำนวนทั้งหมด ("แสดง 1–25" แทน "แสดง 10 จาก 1,344")
เพราะรายการใช้ cursor ตาม agent-history ซึ่งไม่นับทั้งหมด หน้าละ 25 แถว

### 3.3 Console: รายละเอียดเคส

ยึด `mockups/people.html` view `contact-360`: ตัวตนและ action อยู่บนสุด, เนื้อหาหลักซ้าย 2/3, สรุปขวา 1/3

| ส่วน | Component |
| --- | --- |
| ลิงก์กลับ "กลับรายการเคส" | `Button ghost` (คืน filter จาก URL) |
| หัวเคส: h1 หัวข้อ (wrap สูงสุด 2 บรรทัด, `max-width` 62ch) + `StatusChip` + บรรทัด meta (ลูกค้า, ผู้รับผิดชอบ, อัปเดตล่าสุด) | `StatusChip` |
| Action บนขวา | `Button` secondary + primary หนึ่งปุ่ม |
| แถบ conflict / ปิดแล้ว | แถบข้อความในแอป `role="alert"` / `role="status"` |
| ไทม์ไลน์ | local `CaseTimeline` (`<ol>`): ไอคอน + ข้อความ + `<time>`; โน้ต `white-space: pre-wrap`, ยาวเกิน 300 ตัวอักษรตัดที่ 6 บรรทัด และมีปุ่ม "แสดงทั้งหมด" (`aria-expanded`) |
| เพิ่มโน้ต | `TextField multiline` + `Button` "บันทึกโน้ต" |
| สรุปเคส | `<dl>`: สถานะ, ผู้รับผิดชอบ, ทีม, เปิดโดย, เปิดเมื่อ, ปิดเมื่อ (ถ้ามี), งานที่ผูก |
| ลูกค้า | ชื่อและบริษัท (อ่านอย่างเดียว) ไม่มีปุ่มไปโปรไฟล์ เพราะ Console ยังไม่มี route โปรไฟล์ลูกค้ารายคน (ข้อ 8 คำถาม 11) |
| มอบหมาย | `DialogTrigger` + `Dialog` + `Select` |
| ปิดเคส | `Dialog role="alertdialog"` + `Button variant="danger"` |

**ต่างจากหน้าอ้างอิง**: ไม่มีแถบเตือนคงที่ใต้หัว (contact-360 ใช้สำหรับ consent) ใช้ตำแหน่งเดียวกันสำหรับ conflict เท่านั้น
และไทม์ไลน์เป็นรายการแนวตั้ง ไม่ใช่ตาราง เพราะโน้ตยาวหลายบรรทัด

ลำดับไทม์ไลน์: เก่าไปใหม่ (เรียงตาม `occurred_at` แล้วตาม sequence) ช่องเพิ่มโน้ตอยู่ท้าย เพื่อให้อยู่ติดรายการล่าสุด
ตอนเปิดเคสจะมีสามรายการเวลาเดียวกัน: `OPENED` ("{actor} เปิดเคส และให้ {assignee} เป็นผู้รับผิดชอบ"), `INTERACTION_LINKED`
และ `NOTE` (โน้ตแรก) ไทม์ไลน์ยาวเกิน 50 รายการแสดง 50 รายการล่าสุด และมีปุ่ม "โหลดรายการก่อนหน้า (n)" ด้านบน

## 5. คีย์บอร์ดและ focus

**Workspace**
- ลำดับ tab ในแถบบริบท: ชื่อผู้โทร → ปุ่มเปิดเคส จากนั้น phonebar และแท็บหลักตามเดิม
- กด **เปิดเคส** → เปิด inspector (ถ้าปิดอยู่), เลือกแท็บเคส, focus ช่องหัวข้อ ถ้ามีเคสที่สร้างแล้ว focus หัวข้อ "เปิดเคสแล้ว"
- ในแท็บเคส: หัวข้อ → โน้ตแรก → ผู้รับผิดชอบ → เปิดเคส → ล้างร่าง (กรณี unlinked ปุ่ม "ไปเลือกลูกค้า" มาก่อนสรุป)
- `Ctrl/⌘+Enter` ในช่องโน้ตแรกส่งฟอร์ม (Enter ธรรมดาขึ้นบรรทัดใหม่) ไม่เพิ่ม shortcut ระดับหน้า เพราะ Workspace ใช้คีย์กับสายอยู่แล้ว
- **ไปเลือกลูกค้า** → สลับแท็บหลักเป็น Customer 360 และ focus ช่องค้นหาลูกค้า
- สำเร็จ: focus ย้ายไปที่หัวข้อ "เปิดเคสแล้ว" (`tabIndex=-1`) ข้อความประกาศผ่าน `aria-live="polite"` แต่ไม่ย้าย focus ออกจากแผง
  ถ้าผู้ใช้กำลังพิมพ์ใน Customer 360

**Console รายการ**
- Filter สถานะ → ผู้รับผิดชอบ → ล้างตัวกรอง → ตาราง (ใช้ลูกศรตาม React Aria `Table`) → ปุ่มเปลี่ยนหน้า
- `Enter` บนแถวหรือปุ่ม "เปิด" ไปที่รายละเอียด; Back ของเบราว์เซอร์กลับมาที่ filter เดิมและ focus แถวที่เปิดล่าสุด

**Console รายละเอียด**
- ลำดับ: กลับรายการ → action บนขวา (ซ้ายไปขวา) → แถบ conflict (ถ้ามี) → ไทม์ไลน์ (ลิงก์/ปุ่มแสดงทั้งหมด) → ช่องเพิ่มโน้ต → บันทึกโน้ต → การ์ดลูกค้า
- `Ctrl/⌘+Enter` ในช่องโน้ตเท่ากับ "บันทึกโน้ต"; หลังบันทึก focus อยู่ที่ช่องโน้ต (ว่าง) เพื่อเขียนต่อได้
- Dialog มอบหมาย: focus แรก `Select`; Escape/ยกเลิก ปิดและคืน focus ไปปุ่มมอบหมาย; สำเร็จคืน focus ไปปุ่มมอบหมาย
- Dialog ปิดเคส: focus แรก **ยกเลิก** (action ย้อนไม่ได้); Escape ปิด; สำเร็จ focus ไปแถบ "เคสนี้ปิดแล้ว"
- เปลี่ยนสถานะสำเร็จ: ปุ่มชุดใหม่แทนที่ปุ่มเดิม ให้ focus ปุ่มแรกของชุดใหม่ (ไม่ปล่อย focus หลุดไป `body`)
- Conflict: focus ไปที่แถบเตือน (`tabIndex=-1`, `role="alert"`); "โหลดเคสล่าสุด" แล้ว focus ช่องโน้ตถ้ามีร่าง

## 8. คำถามที่ต้องตัดสิน

เรียงจากผลกระทบมากไปน้อย mockup ใช้ตัวเลือกที่แนะนำแล้วทุกข้อ

1. **ฟอร์มเปิดเคสใน Workspace เป็น modal dialog หรือ panel** (issue/Lead ใช้คำว่า "dialog")
   - ก. **แท็บ "เคส" ในแผงงานแบบ non-modal (แนะนำ)** ไม่ขวางปุ่มควบคุมสายตามหลักการข้อ 4 ร่างอยู่รอดเมื่อสลับแท็บ
   - ข. `Dialog` modal ง่ายกว่า แต่ระหว่าง `ACTIVE` จะบังปุ่มวางสายและพักสาย
2. **ปิดเคสได้จาก `OPEN` โดยตรงหรือไม่**
   - ก. **ไม่ได้ ต้องผ่าน `RESOLVED` ก่อน (แนะนำ)** ตรงกับลำดับ `OPEN → RESOLVED → CLOSED` ใน issue และทำให้ปิดผิดยากขึ้น
   - ข. ได้จากทั้งสองสถานะ ลดคลิกหนึ่งครั้ง
3. **เปิดเคสหลังบันทึกผล (wrapup) แล้วได้หรือไม่**
   - ก. **ไม่ได้ในรอบนี้ ใช้แถบทางลัดใน wrapup เมื่อเลือก "ต้องติดตามต่อ" แทน (แนะนำ)** ตรงกับขอบเขต ACTIVE/WRAPUP
   - ข. เปิดได้จากงานในรายการ "ปิดแล้ว" ของ session ด้วย ต้องเพิ่มกฎสิทธิ์ของงานที่จบแล้วใน API
4. **ค่าเริ่มต้นของ filter รายการ**
   - ก. **สถานะ "ยังไม่ปิด" + ผู้รับผิดชอบ "ของฉัน" (แนะนำ)** เอเจนต์เข้ามาเพื่อตามงานของตัวเองเป็นหลัก
   - ข. "ยังไม่ปิด" + "ทั้งทีม" ตรงกับชื่อหน้า "เคสของทีม"
5. **ทีมของเคสเมื่อ Agent ย้ายทีม**
   - ก. **เคสอยู่กับทีมที่เปิด (`team_id` บนเคส) ผู้ที่ย้ายทีมจะไม่เห็นเคสเดิม และสรุปเคสแสดง "ไม่อยู่ในทีมแล้ว" ให้มอบหมายใหม่ (แนะนำ)**
   - ข. เคสย้ายตามผู้รับผิดชอบ ทำให้กฎสิทธิ์ซับซ้อนและข้ามทีมได้
6. **โน้ตต้องผ่าน `expectedVersion` เหมือนคำสั่งอื่นหรือไม่**
   - ก. **ใช่ ตามเกณฑ์จบใน issue และเก็บร่างไว้เมื่อ conflict (แนะนำ)**
   - ข. โน้ตเป็น append-only ไม่ตรวจ version ลด conflict ในเคสที่หลายคนเขียนพร้อมกัน แต่ต้องแก้เกณฑ์จบ
7. **ค้นหาตามหัวข้อหรือชื่อลูกค้าในรายการ**
   - ก. **ยังไม่มีในรอบนี้ ใช้ filter สองตัว (แนะนำ)** API รอบนี้ไม่มี search และการค้นชื่อลูกค้าแตะ PII
   - ข. เพิ่ม `SearchField` ค้นหัวข้อ (ไม่ค้นชื่อลูกค้า)
8. **บันทึก `ASSIGNED` ตอนเปิดเคสหรือไม่**
   - ก. **ไม่ ข้อความ `OPENED` บอกผู้รับผิดชอบแรกแล้ว `ASSIGNED` ใช้เฉพาะการเปลี่ยนมือภายหลัง (แนะนำ)**
   - ข. บันทึกทุกครั้ง แม้มอบหมายให้ตัวเอง ทำให้ไทม์ไลน์ซ้ำ
9. **ลิงก์ "เปิดในประวัติงาน" ในไทม์ไลน์**
   - ก. **แสดงเฉพาะงานของผู้ดูเอง เพราะ agent-history เห็นเฉพาะงานตัวเอง (แนะนำ)** API ส่ง flag ว่าผู้ดูเป็นเจ้าของงานหรือไม่
   - ข. ไม่แสดงลิงก์เลยในรอบนี้
10. **การแบ่งหน้าและจำนวนรวม**
    - ก. **cursor หน้าละ 25 แสดง "แสดง 1–25" ไม่มีจำนวนรวม (แนะนำ)** ใช้ pattern ของ agent-history และไม่ต้อง count
    - ข. แสดงจำนวนรวมแบบหน้าอ้างอิง ต้องเพิ่ม count query
11. **ลิงก์จากเคสไปโปรไฟล์ลูกค้า**
    - ก. **ยังไม่มีในรอบนี้ การ์ดลูกค้าแสดงชื่อและบริษัทเท่านั้น (แนะนำ)** `customer-overview` ใน Console ยังไม่มี deep link รายคน
    - ข. เพิ่ม route โปรไฟล์ลูกค้ารายคน (ไม่มี PII ใน URL ใช้ contact id) แล้วใส่ปุ่ม "เปิดโปรไฟล์ลูกค้า" ในการ์ด
