# ADR 017: Interaction Analytics — วิเคราะห์ 100% ของบทสนทนา แต่แยกออกจากการให้คะแนน

- **สถานะ:** Accepted
- **วันที่:** 2026-08-08

## บริบท

[ADR-010](010-quality-management.md) สร้าง transcript + category DSL ไว้แล้ว แต่ใช้กับ
**สายที่ถูกสุ่มมาตรวจ** เป็นหลัก ส่วนที่คู่แข่งขายแพงที่สุด (NICE Interaction Analytics,
Zoom Revenue Accelerator) คือการวิเคราะห์ **ทุกบทสนทนา** เพื่อตอบคำถามระดับธุรกิจ:
ลูกค้าโทรมาเรื่องอะไรมากที่สุด, เรื่องไหนกำลังโต, เรื่องไหนทำให้ AHT ยาว, เรื่องไหนทำให้ยกเลิกบริการ

## การตัดสินใจ

1. **วิเคราะห์ทุก interaction ที่มี transcript — ไม่ผูกกับ quality plan**
   sampling เป็นเรื่องของการ*ประเมินคน* (ต้องยุติธรรมและมีคนอ่านทุกใบ)
   ส่วน analytics เป็นเรื่องของการ*เข้าใจงาน* ซึ่งต้องครบถึงจะเชื่อได้
   ปนกันเมื่อไหร่จะได้ข้อสรุปธุรกิจจากตัวอย่าง 2% ซึ่งอันตรายกว่าไม่มีข้อมูล

2. **Topic discovery แยกจาก category ที่คนเขียนกฎเอง — และทั้งสองอยู่ร่วมกัน**
   category DSL (คนเขียนกฎ, แม่นยำ, อธิบายได้) ตอบว่า "มีสายที่เข้าเงื่อนไขนี้กี่สาย"
   topic discovery (จัดกลุ่มอัตโนมัติ) ตอบว่า "มีเรื่องอะไรที่เราไม่เคยตั้งกฎไว้"
   เรื่องที่ค้นพบต้อง **เลื่อนขั้นเป็น category ได้ด้วยคลิกเดียว** — ไม่งั้นการค้นพบไม่มีปลายทาง

3. **ผลวิเคราะห์เก็บเป็น aggregate รายช่วงเวลา ไม่ query ดิบทุกครั้ง**
   `ia_topic_intervals` (15 นาที) เป็นตารางสรุปแบบเดียวกับ `wfm_interval_stats`
   ([ADR-008](008-workforce-management.md)) — ทำให้หน้าจอเปิดเร็วและต้นทุนคงที่

4. **Sentiment ต้องรายงานเป็นแนวโน้มของกลุ่ม ห้ามใช้ตัดสินสายเดี่ยว**
   ความแม่นยำของ sentiment ภาษาไทยไม่พอสำหรับการตัดสินรายบุคคล แต่พอสำหรับดูทิศทางรวม
   ข้อจำกัดนี้ต้องเขียนบนหน้าจอ ไม่ใช่ซ่อนใน docs

5. **ไม่มี data warehouse ใหม่ใน v1** — ใช้ Postgres + ตารางสรุป
   ถ้าวันหนึ่งข้อมูลโตเกิน ให้ส่งออกผ่าน data feed ของ
   [ADR-019](019-reporting-data-platform.md) ไปยังคลังข้อมูลของลูกค้า ไม่ใช่สร้างคลังของเราเอง

6. **ทุกตัวเลขต้องคลิกลงไปเห็นสายจริงได้เสมอ (drill to evidence)**
   ตัวเลขที่คลิกลงไปดูของจริงไม่ได้ คือตัวเลขที่ไม่มีใครกล้าใช้ตัดสินใจ
   หลักการเดียวกับ evidence contract ของ auto-QM

## ผลที่ตามมา

- worker ของ `apps/qm` ได้ job ชนิดใหม่ `TOPIC` และ `AGGREGATE` (ไม่มี service ใหม่)
- ต้องมี embedding ของ transcript (ใช้ pgvector ตัวเดียวกับ KB ใน [ADR-013](013-virtual-agent-knowledge.md))
- entitlement: `modules.analytics.{enabled, categories, topicDiscovery, sentiment, correlation}`
  + quota `analyzedMinutesPerMonth`
- `qm.analytics` เดิมใน [licensing §2](../licensing.md) ถูกยกระดับเป็น `modules.analytics.*`
  โดยคง key เดิมไว้เป็น alias หนึ่งรอบ release (key คือสัญญาถาวร)

## ทางเลือกที่ไม่เอา

| ทางเลือก | เหตุผลที่ไม่เอา |
|---|---|
| วิเคราะห์เฉพาะสายที่ถูกสุ่มตรวจ | ข้อสรุปธุรกิจจากตัวอย่าง 2% |
| ใช้ topic discovery แทน category ไปเลย | อธิบายที่มาไม่ได้ ใช้กับ compliance ไม่ได้ |
| ตั้ง ClickHouse/BigQuery ของเราเอง | เพิ่มโครงสร้างพื้นฐานที่ต้องดูแล ก่อนจะรู้ว่าลูกค้าต้องการรูปไหน |
| ให้ sentiment ปรากฏใน scorecard รายคน | ความแม่นยำไม่พอ และจะถูกใช้ผิดทันที |
