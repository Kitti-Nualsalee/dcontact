# ADR 020: Customer 360 — identity resolution เป็นของระบบเรา และการรวมคนสองคนต้องย้อนกลับได้

- **สถานะ:** Accepted
- **วันที่:** 2026-08-08

## บริบท

`contacts` ปัจจุบันเป็นตาราง CRUD ธรรมดา — เก็บชื่อ เบอร์ อีเมล LINE ID ไว้ในแถวเดียว
แต่ความจริงคือ ลูกค้าคนเดียวกันเข้ามาด้วย identity คนละตัวทุกช่องทาง
(เบอร์โทร, LINE userId, Facebook PSID, อีเมล, เลขลูกค้าใน CRM)
ถ้าเชื่อมกันไม่ได้ คำว่า "omnichannel" ในหน้าขายเป็นแค่คำโฆษณา —
agent ยังต้องถามซ้ำทุกครั้งว่า "เมื่อวานคุยกับใครไว้ครับ"

## การตัดสินใจ

1. **แยก `contacts` (คน) ออกจาก `contact_identities` (ช่องทางที่เขาใช้)**
   1 contact : N identity — identity ใหม่ที่ยังไม่รู้ว่าเป็นใคร สร้าง contact ชั่วคราวได้
   นี่คือ schema change ที่ต้องทำก่อนที่ข้อมูลจริงจะสะสมมากเกินกว่าจะย้าย

2. **การจับคู่มี 3 ระดับความมั่นใจ และมีเพียงระดับเดียวที่รวมอัตโนมัติ**
   - **แน่นอน** (identity ตรงกับที่ยืนยันแล้ว, เลขลูกค้าจาก CRM) → รวมอัตโนมัติ
   - **น่าจะใช่** (เบอร์เดียวกันแต่ชื่อไม่ตรง, อีเมลเดียวกัน) → **เสนอให้คนยืนยัน**
   - **เดา** (ชื่อคล้ายกัน) → ไม่ทำอะไร แสดงเป็นข้อมูลประกอบเท่านั้น
   การรวมอัตโนมัติจากการเดาคือการทำให้ข้อมูลลูกค้าสองคนปนกัน ซึ่งเป็นปัญหา PDPA ทันที

3. **การรวม (merge) ต้องย้อนกลับได้เสมอ**
   ไม่ลบแถว — ทำเป็น `merged_into` + เก็บ `contact_merge_log` ที่ย้อนกลับได้ 90 วัน
   ระบบที่รวมแบบทำลายข้อมูลจะมีวันที่ต้องอธิบายกับลูกค้าว่าประวัติเขาหายไปไหน

4. **โปรไฟล์ 360 เป็น "มุมมอง" ไม่ใช่ตารางใหม่**
   ประกอบจาก interactions + cases + fb_responses + ob_attempts + CRM ภายนอก ณ เวลาที่เปิดดู
   การ denormalize เป็นตารางสรุปจะเก่าทันทีและสร้างสำเนาข้อมูลส่วนบุคคลเพิ่มโดยไม่จำเป็น

5. **ข้อมูลจาก CRM ภายนอกไม่ถูกคัดลอกมาเก็บ — ดึงสดตอนเปิดดู**
   ผ่าน [integration platform](015-integration-platform.md) พร้อม cache สั้น ๆ (60 วินาที)
   เราไม่ใช่เจ้าของข้อมูลนั้น และการเก็บสำเนาแปลว่าต้องรับผิดชอบตาม PDPA เพิ่มโดยไม่ได้อะไร

6. **สิทธิของเจ้าของข้อมูล (PDPA) ทำงานที่ระดับ contact**
   ขอดู/ขอลบ/ขอแก้ ต้องทำได้จากหน้าเดียวและครอบคลุมทุกโมดูลที่อ้างถึง contact นั้น
   (รวมถึงเสียง transcript และ DNC) — ออกแบบตั้งแต่ตอนนี้แม้จะทำจริงในเฟสหลัง

## ผลที่ตามมา

- schema: `contacts` เพิ่ม `merged_into`, `verified_at`; ตารางใหม่ `contact_identities`,
  `contact_merge_log`; consent/preference/restriction เป็น `cg_*` ของ [ADR-027](027-contact-governance.md)
- router/flow ใช้ identity resolution ตอนสายเข้าเพื่อดึงประวัติ (ไม่ใช่แค่จับคู่เบอร์)
- entitlement: `modules.customer360.{enabled, identityResolution, externalProfile, dsar}`

## ทางเลือกที่ไม่เอา

| ทางเลือก | เหตุผลที่ไม่เอา |
|---|---|
| เก็บทุก identity เป็นคอลัมน์ใน `contacts` | รองรับได้ช่องทางละหนึ่งค่าตลอดกาล และเพิ่มช่องทางใหม่ = schema change |
| รวมอัตโนมัติทุกอย่างที่คล้ายกัน | ข้อมูลลูกค้าสองคนปนกัน — ผิด PDPA และกู้คืนยาก |
| merge แบบลบแถวที่ซ้ำ | ย้อนกลับไม่ได้ ประวัติหาย |
| คัดลอกโปรไฟล์จาก CRM มาเก็บ | สำเนาข้อมูลส่วนบุคคลที่เก่าและต้องรับผิดชอบเพิ่ม |
