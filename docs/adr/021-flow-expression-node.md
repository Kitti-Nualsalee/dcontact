# ADR 021: Expression node ใน Flow — ให้ทางออกสำหรับ logic ที่ซับซ้อน แต่เป็น sandbox ไม่ใช่ภาษาสคริปต์

- **สถานะ:** Accepted
- **วันที่:** 2026-08-09

## บริบท

[ADR-007](007-flow-engine.md) จงใจจำกัด node ไว้แค่ 13 ชนิด (ตอนนี้ 18) เพื่อให้หัวหน้าทีมแก้ผังเองได้
โดยไม่ต้องจ้างพาร์ตเนอร์ — ต่างจาก NICE CXone ที่มี action หลักร้อยและมี **Snippet**
(ภาษาสคริปต์เฉพาะของตัวเอง) ให้เขียนโค้ดในผังได้เต็มรูป

ปัญหาที่จะเกิดแน่นอนเมื่อระบบถูกใช้จริง: `setvar` + `condition` ทำได้แค่ระดับ "เท่ากับ / มากกว่า / อยู่ในลิสต์"
แต่เคสจริงจะมีของแบบนี้เสมอ —
แปลงรูปแบบเบอร์ให้เป็น E.164 ก่อนส่ง API · อ่านค่าลึก ๆ จาก JSON ที่ CRM ตอบกลับมา ·
คำนวณ tier จากยอดซื้อสามช่วง · ตัดคำนำหน้าชื่อ · รวมข้อความจากหลายตัวแปร

ทางเลือกที่มีอยู่วันนี้มีสองทางและทั้งคู่ไม่ดี: (ก) ให้ลูกค้ารอทีม dev ทำ API ให้ ซึ่งฆ่าคุณค่า
"หัวหน้าทีมแก้เองได้" (ข) ยัด logic ไปไว้ในระบบปลายทางแล้วเรียกผ่าน `api` ซึ่งได้ latency
เพิ่มหนึ่งรอบเน็ตเวิร์กสำหรับการคำนวณที่ใช้เวลาไม่ถึงมิลลิวินาที

## การตัดสินใจ

1. **มี node `expression` — แต่เป็นนิพจน์ ไม่ใช่โปรแกรม**
   หนึ่ง node = **หนึ่งนิพจน์ที่คืนค่าหนึ่งค่า** แล้ว assign ลงตัวแปรเดียวที่ประกาศไว้แล้ว
   ไม่มี statement, ไม่มีการประกาศตัวแปรใหม่, ไม่มี side effect
   นี่คือเส้นที่แยก "ทางออกสำหรับ logic" ออกจาก "ภาษาสคริปต์ในผัง"

2. **ห้าม I/O ทุกชนิด**
   ไม่มี network, ไม่มี filesystem, ไม่มี timer, ไม่มี `require`/`import`, ไม่มี global object ของ runtime
   อยากคุยกับข้างนอกให้ใช้ `api` ซึ่งมี timeout, retry, ตัวเชื่อมที่มีเจ้าของ และเห็นใน trace

3. **ห้ามลูปอิสระ** — มีเฉพาะ `map` / `filter` / `reduce` บน array ที่มีขนาดจำกัด
   `while` และ `for` เปิดทางให้ผังวนไม่จบบนสายที่ลูกค้ารออยู่ ซึ่งเป็นความเสียหายที่ไม่โผล่ในการทดสอบ

4. **เพดานที่บังคับด้วย runtime ไม่ใช่ด้วยเอกสาร**
   ≤ 50 ms · ≤ 4 MB · ผลลัพธ์ต้องเป็นชนิดเดียวกับที่ประกาศใน `variables[]`
   เกินอย่างใดอย่างหนึ่ง = kill แล้วเดินเส้น `error` (ตามสัญญา `onError` ใน
   [flow-engine §5.5](../flow-engine.md))

5. **ปล่อยใช้หลังมีเคสจริงอย่างน้อย 3 เคสที่ `setvar` ทำไม่ไหว** (เฟส FL4)
   ถ้าเปิดตั้งแต่วันแรก `expression` จะกลายเป็น**ทางออกแรก**ที่ทุกคนเลือกใช้แทนที่จะเป็นทางออกสุดท้าย
   แล้วผังจะเต็มไปด้วยโค้ดภายในหนึ่งไตรมาส

6. **สิ่งที่นิพจน์มองเห็นเป็นแบบอ่านอย่างเดียวและถูก mask แล้ว**
   `vars`, `contact`, `interaction` เท่านั้น — ตัวแปรที่ประกาศ `sensitive: true` มาถึงในรูปที่ mask แล้ว
   (กันการเขียนนิพจน์เพื่อ "แกะ" เลขบัตรออกมาใส่ตัวแปรธรรมดาแล้วหลุดเข้า trace)

7. **นิพจน์ทุกตัวปรากฏใน flow trace พร้อม input/output ที่ mask แล้ว**
   สิ่งที่แก้ไม่ได้ใน Snippet ของเจ้าอื่นคือ "ทำไมมันคำนวณออกมาเป็นค่านี้" — เราตอบได้เพราะ
   นิพจน์เป็น pure function ที่มีบันทึกครบ

## ผลที่ตามมา

- ต้องมี interpreter ที่แยกจาก JS ของ host — ตัวเลือกที่ตั้งใจไว้คือ **นิพจน์ชุดจำกัดที่เรา parse เอง**
  หรือ QuickJS/isolated-vm ที่ปิด host binding ทั้งหมด (`node:vm` เปล่า ๆ **ไม่นับว่าเป็น sandbox**)
- Flow Designer ต้องมี **ตัวทดสอบนิพจน์แบบสด** ในกล่อง inspector (ใส่ค่าตัวอย่าง → เห็นผลทันที)
  ไม่งั้นคนจะไปทดสอบด้วยสายจริง
- ต้องมีรายงาน "นิพจน์ที่ถูกใช้ทั้งหมดใน tenant นี้" ให้ review เป็นรอบ — นิพจน์ที่ยาวเกิน N อักขระ
  คือสัญญาณว่าควรเป็น API หรือ node ใหม่
- entitlement: อยู่ใต้ `modules.flows` เดิม ไม่แยกขาย — แต่จำกัดได้ต่อ tenant ถ้าลูกค้าไม่ต้องการเปิด

## ทางเลือกที่ไม่เอา

| ทางเลือก | เหตุผลที่ไม่เอา |
|---|---|
| ภาษาสคริปต์เต็มรูปแบบ Snippet ของ NICE | เปิดแล้วปิดไม่ได้ · ผังกลายเป็นโค้ดที่ไม่มีใคร review · ต้องมีทีมซัพพอร์ตที่อ่านโค้ดลูกค้าออก |
| ไม่มีเลย ให้ไปทำที่ API ปลายทาง | ฆ่าคุณค่า "หัวหน้าทีมแก้เองได้" และเพิ่ม latency หนึ่งรอบเน็ตเวิร์กเพื่อคำนวณ 0.2 ms |
| ใช้ `node:vm` เปล่า ๆ | ไม่ใช่ขอบเขตความปลอดภัยจริง — หลุดออกมาถึง host ได้ |
| ให้เขียน JS ได้แต่ห้ามด้วยเอกสาร | ข้อห้ามที่ไม่ได้บังคับด้วย runtime คือข้อห้ามที่จะถูกละเมิดในเดือนที่สาม |
| อนุญาต `while` แต่ใส่ตัวนับกันวนไม่จบ | ได้ความซับซ้อนของลูปโดยไม่ได้ประโยชน์ที่ `map/filter/reduce` ให้ไม่ได้ |
