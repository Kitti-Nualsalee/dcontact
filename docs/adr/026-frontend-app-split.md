# ADR 026: แบ่งแอปหน้าจอตาม "งานที่มีชีวิต" ไม่ใช่ตามบทบาท

- **สถานะ:** Accepted
- **วันที่:** 2026-08-14

## บริบท

mockup ทั้งหมดวันนี้เป็น shell เดียวที่มี 15 พื้นที่บน rail ตั้งแต่กล่องงานของเอเจนต์
ไปจนถึงการตั้งค่า tenant และใบเสร็จ — เหมาะกับการออกแบบ แต่ถ้าปล่อยให้กลายเป็นโครงของโค้ดจริง
เราจะได้แอปเดียวที่ **แก้หน้ารายงานแล้วต้องรีโหลดจอของคนที่กำลังคุยสายอยู่ 40 คน**

โค้ดโครงร่างเดิม (`apps/agent-desktop` + softphone SIP.js) ถูกลบทิ้งเมื่อ 2026-08-14 ระหว่างออกแบบ
จึงเป็นจังหวะที่ตัดสินเรื่องนี้ได้โดยไม่มีหนี้ต้องย้าย

แรงกดดันสามอย่างที่ทำให้ต้องตัดสินตอนนี้ ไม่ใช่ตอนเริ่มเขียนโค้ด:

1. **จังหวะ deploy ไม่เท่ากัน** — หน้าตั้งค่า/รายงานแก้ทุกสัปดาห์ หน้าทำงานควรแก้ให้น้อยและมีพิธีกรรม
2. **presence ต้องมีแหล่งเดียว** ([ADR-022](022-internal-collaboration.md)) — ถ้าหลายหน้าจอต่อ WS
   ด้วย identity เดียวกัน เอเจนต์คนเดียวจะได้ routing offer หลายที่และสถานะขัดกันเอง
3. **ขนาด bundle** — workspace คือแอปที่เปิดค้าง 8 ชั่วโมง ไม่ควรลาก grid ของ WFM,
   chart ของ analytics และ flow editor ติดไปด้วย

## การตัดสินใจ

1. **แบ่งเป็นสองแอป ไม่ใช่สาม และเส้นแบ่งคือ "ต้องมีงานอยู่ในมือหรือไม่"**

   | แอป | มีอะไร | เหตุผลที่อยู่ด้วยกัน |
   |---|---|---|
   | `apps/workspace` | กล่องงาน · softphone · consult/chat ([ADR-022](022-internal-collaboration.md)) · แผง case/journey/assist · wrap-up · **หน้าสดของหัวหน้า**: team pulse, live interactions, monitor/whisper/barge, queue control, alerts | ทุกอย่างต้องการ *session ที่มีชีวิต* — WebRTC, WS, presence, สถานะที่หายไม่ได้ · monitor/whisper ใช้ media stack ตัวเดียวกับสายปกติ |
   | `apps/console` | routing/flows · people · integrations · WFM setup · QM forms/plans/สอบทาน · campaigns · journeys · reports/analytics · admin/licensing | เป็น CRUD + ตาราง หนักแต่รีเฟรชแล้วไม่มีอะไรพัง · deploy บ่อยได้โดยไม่แตะคนที่กำลังคุยสาย |

   **ห้ามแบ่งตามบทบาท** — หัวหน้าก็รับสาย, team lead ทำทั้งสองอย่าง, ผู้ประเมิน QM หลายคนเป็นเอเจนต์ด้วย
   แบ่งตามบทบาทแปลว่าต้องมีสองแอปที่ทั้งคู่ต้องมี WebRTC + WS + presence ครบ — ทำส่วนที่ยากที่สุดซ้ำสองรอบ
   บทบาทเป็นตัวกำหนด **เมนูที่เห็น** ผ่าน entitlement/permission ([ADR-009](009-plan-entitlement-licensing.md)) ไม่ใช่ตัวกำหนดแอป

   เกณฑ์ตัดสินเวลามีหน้าใหม่: *ถ้าคนกดต้องกดระหว่างเหตุการณ์กำลังเกิด → workspace ·
   ถ้ากดหลังเหตุการณ์จบแล้ว → console* (wallboard สด/queue control อยู่ workspace,
   รายงานย้อนหลังของคิวเดียวกันอยู่ console)

2. **แท็บทำงานมีได้แท็บเดียว และมันคือแท็บเดียวที่ประกาศว่า "รับงานได้"**
   workspace ต้องทำ leader election (`BroadcastChannel` + heartbeat ใน `localStorage`)
   แท็บที่ไม่ใช่ leader แสดงหน้าจอ "แท็บนี้ไม่ใช่แท็บทำงาน — กดเพื่อย้ายมาที่นี่" และ**ไม่ต่อ WS ของ routing**
   ถ้าไม่ทำ: เปิดสองแท็บ = ack countdown เดินสองอัน, งานเดียวถูกกดรับสองที่, presence กระพริบ
   `apps/console` **ห้ามต่อ WS ของ routing เลย** ต่อได้แค่ช่องอ่านอย่างเดียว (แดชบอร์ด/แจ้งเตือน)

3. **console เปิดเป็นแท็บใหม่เสมอ ห้าม navigate ทับ workspace**
   ลิงก์ข้ามแอปทุกจุดต้องพกบริบทไปด้วย (`?case=CS-4821`, `?interaction=…`, `?journey=…`)
   ไม่ใช่เปิดหน้าเปล่าแล้วให้คนไปค้นเอง — เพราะคนกดคือคนที่กำลังคุยกับลูกค้าอยู่

4. **SSO เงียบข้ามแอป** — สองแอปอยู่คนละ subdomain แต่ session เดียวผ่าน Keycloak ([ADR-004](004-keycloak-iam.md))
   token หมดอายุระหว่างคุยสายต้อง refresh เงียบ ๆ **ห้าม redirect ไปหน้า login ระหว่างมี interaction ในมือ**
   ถ้า refresh ไม่สำเร็จจริง ๆ ให้เตือนบนจอและกันไม่ให้รับงานใหม่ แทนการเด้งออกทันที

5. **การอัปเดตเวอร์ชันต้องรอจังหวะของคน ไม่ใช่จังหวะของ deploy**
   workspace เช็ก build version กับ API แล้วขึ้นแถบ "มีเวอร์ชันใหม่ · รีโหลดเมื่อว่าง"
   บังคับรีโหลดได้เฉพาะตอนไม่มีงานในมือและไม่อยู่ใน wrap-up
   console รีโหลดเองได้ทันที

6. **UI ร่วมกันที่ `packages/ui` ห้าม fork component**
   design token/สี/ปุ่ม/ตาราง/สถานะช่องทาง มาจากที่เดียว (วันนี้คือ `mockups/assets/app.css` ฉบับร่าง)
   ถ้าไม่มีแพ็กเกจนี้ตั้งแต่วันแรก สองแอปจะดริฟต์ภายในสามเดือน

7. **เบราว์เซอร์ก่อน desktop shell ทีหลัง — และ shell ต้องไม่ fork UI**
   เหตุที่ *บังคับ* ให้มี native shell มีจริงแต่อยู่ปลายทางทั้งนั้น: บันทึกหน้าจอของ QM
   (Q6+ ตาม [ADR-010](010-quality-management.md) ระบุเองว่าต้องมี client ฝั่งเอเจนต์) ·
   ควบคุมสายจากปุ่มบนหูฟัง (HID) · hotkey ตอนแอปไม่ได้โฟกัส · บังคับเวอร์ชันบนเครื่องลูกค้า
   ถ้าเริ่มที่ Electron วันนี้ เราจะได้ปัญหา distribution/auto-update/AV false-positive
   มาแลกกับฟีเจอร์ที่ยังไม่ได้ทำ — shell เมื่อมาต้องเป็นเปลือกบางที่โหลด UI ตัวเดียวกัน

8. **มือถือของหัวหน้า = PWA ไม่ใช่ native** — ดูตัวเลข อนุมัติคำขอ รับแจ้งเตือน เท่านั้น
   ไม่มีการรับสายบนมือถือใน v1

9. **mockup ยังเป็น shell เดียวต่อไป** — มันคือเครื่องมือออกแบบและ demo การเดินเรื่อง
   แต่เอกสารต้องบอกเส้นแบ่งไว้ (ตารางข้อ 1) เพื่อไม่ให้ใครอ่าน rail แล้วเข้าใจว่าเป็นแอปเดียว

## ผลที่ตามมา

- `README.md` เปลี่ยนจาก `apps/agent-desktop` เป็น **`apps/workspace` + `apps/console`** และเพิ่ม `packages/ui`
- งานแรกของเฟส 1 ฝั่ง frontend ไม่ใช่หน้าจอ แต่คือ **leader election + สัญญา WS เส้นเดียว** —
  ทำทีหลังแปลว่าต้องรื้อทุกหน้าที่ subscribe ไปแล้ว
- ต้องมี endpoint `GET /api/v1/version` (หรือ header) ให้ workspace เทียบ build ของตัวเอง
- [iam-architecture.md](../iam-architecture.md): เพิ่มข้อกำหนด silent refresh + กติกา
  "ห้าม redirect login ระหว่างถืองาน"
- entitlement ไม่เปลี่ยนรูปแบบ — สิทธิ์ยังคุมเมนู ไม่ใช่คุมแอป ([licensing.md](../licensing.md))
- QM screen recording ยังอยู่ Q6+ เหมือนเดิม แต่ตอนถึงเวลาจะเป็น **shell ห่อ workspace** ไม่ใช่แอปที่สาม

## ทางเลือกที่ไม่เอา

| ทางเลือก | เหตุผลที่ไม่เอา |
|---|---|
| แอปเดียวจบเหมือน mockup | deploy หน้ารายงานกระทบคนที่กำลังคุยสาย · bundle บวม · presence ไม่มีเจ้าของ |
| แยกสามแอป agent / supervisor / admin | ทำ WebRTC + WS + presence ซ้ำสองรอบ และบทบาทจริงคาบเกี่ยวกันอยู่แล้ว |
| micro-frontend รวมทุกอย่างใน shell เดียว | ได้ความซับซ้อนของการแยก โดยไม่ได้ประโยชน์ข้อหลัก (แยกจังหวะ deploy จริง ๆ) |
| เริ่มที่ Electron ตั้งแต่วันแรก | จ่ายค่า distribution/auto-update ก่อนจะรู้ว่าต้องใช้ native จริงไหม |
| ปล่อยเรื่องหลายแท็บไว้แก้ทีหลัง | เป็นข้อกำหนดของ *สัญญา WS* ไม่ใช่เรื่อง UI — แก้ทีหลังคือรื้อทุกหน้าที่ subscribe แล้ว |
