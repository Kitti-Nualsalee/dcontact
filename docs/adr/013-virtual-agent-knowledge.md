# ADR 013: Virtual Agent & Knowledge — บอตเป็น "ผู้เล่นใน flow" ไม่ใช่ระบบคู่ขนาน และคลังความรู้เป็นแหล่งความจริงเดียว

- **สถานะ:** Accepted
- **วันที่:** 2026-08-08

## บริบท

[flow-engine.md](../flow-engine.md) มี node `bot` อยู่แล้วแต่เป็นเพียง hook ไปหาระบบภายนอก —
ยังไม่มีสิ่งที่ลูกค้าซื้อจริง: บอตที่ตอบคำถามได้เอง (deflection) และคลังความรู้ที่บอตกับคนใช้ร่วมกัน
คู่แข่งขายเป็นหัวหอก (NICE = Autopilot/Expert, Zoom = Virtual Agent + AI Expert Assist)

ตัวเลขที่โมดูลนี้ต้องขยับคือ **containment rate** (จบได้โดยไม่ต้องใช้คน) ซึ่งกระทบต้นทุนตรง ๆ

## การตัดสินใจ

1. **บอตทำงาน "ใน" flow ไม่ใช่ "แทน" flow**
   node `Bot` เรียก `apps/bot` แล้วรับผลกลับเป็นหนึ่งใน 3 อย่าง:
   `ANSWERED` / `HANDOFF(reason, context)` / `FAILED` — flow เป็นคนตัดสินใจต่อเสมอ
   ทางเลือกที่ให้บอตเป็นเจ้าของบทสนทนาทั้งช่องทางจะทำให้เรามีระบบ routing สองชุด
   และวันที่ต้องอธิบายว่า "ทำไมสายนี้ไม่เข้าคิว" จะไม่มีใครตอบได้

2. **`apps/bot` เป็น TS service ที่เรียก LLM provider — ไม่ฝึกโมเดลเอง**
   วินัยเดียวกับ [ADR-010](010-quality-management.md) ข้อ 1 — งานหนักคือการเรียก provider
   ทำให้ on-prem สลับไปใช้โมเดลในองค์กรได้ด้วยการเปลี่ยน provider ตัวเดียว

3. **Knowledge base เป็นแหล่งความจริงเดียว ใช้ทั้งบอตและคน**
   บทความชุดเดียวกันถูกใช้โดย (ก) บอตในโหมด RAG (ข) agent assist
   ([ADR-014](014-agent-assist.md)) (ค) หน้า self-service ของลูกค้า
   ถ้าแยกคลังกัน จะได้คำตอบที่ต่างกันระหว่างบอตกับคน ซึ่งเป็นข้อร้องเรียนที่แก้ยากที่สุด

4. **บอตห้ามตอบนอกคลังความรู้ (grounded only) และต้องอ้างที่มาเสมอ**
   คำตอบทุกคำตอบต้องแนบ `sources[]` (articleId + chunk) ถ้าไม่มีแหล่งอ้างอิงที่ผ่านเกณฑ์
   ความมั่นใจ ให้ตอบว่าไม่ทราบแล้ว handoff — **สัญญาหลักฐานแบบเดียวกับ auto-QM**
   ([ADR-010](010-quality-management.md) ข้อ 9)

5. **Handoff ต้องส่งบริบทไปทั้งหมด และ agent ต้องเห็นว่าบอตพูดอะไรไปแล้ว**
   บทสนทนากับบอตถูกเขียนเป็น `messages` ของ interaction เดียวกันตั้งแต่ต้น
   (ไม่ใช่เก็บแยกแล้วค่อยแปะ) — ผลคือ QM ตรวจช่วงที่บอตคุยได้ด้วยโดยไม่ต้องทำอะไรเพิ่ม

6. **บอตมีเวอร์ชันและต้องผ่าน test set ก่อน publish**
   เหมือน flow ([flow-engine §6](../flow-engine.md)) — publish บอตที่ยังไม่ผ่านชุดทดสอบไม่ได้
   ชุดทดสอบคือคำถามจริงจาก transcript ที่ถูกติดป้ายไว้ (ได้ฟรีจาก QM)

7. **บทความมี "เจ้าของ + วันหมดอายุ" บังคับ**
   คลังความรู้ที่ไม่มีวันหมดอายุจะกลายเป็นคลังคำตอบผิดภายใน 18 เดือน และเมื่อบอตใช้ RAG
   จากคลังนั้น เราจะ**ขยายความผิดพลาดอัตโนมัติ** แทนที่จะจำกัดมัน

## ผลที่ตามมา

- topic ใหม่ `dc.bot.events` (`bot.answered` / `bot.handoff` / `bot.no_answer` / `kb.gap`)
- `kb.gap` (คำถามที่ไม่มีคำตอบในคลัง) กลายเป็นคิวงานให้ทีมความรู้ — วงจรปรับปรุงตัวเอง
- flow engine: node `Bot` ได้ property เพิ่ม (botId, เกณฑ์ confidence, จำนวนรอบสูงสุด)
- entitlement: `modules.bot.{enabled, faqDeflection, ragAnswer, voiceBot}` +
  `modules.knowledge.{enabled, publicPortal}` + quota `botSessionsPerMonth`
- ต้นทุน LLM เป็นต้นทุนผันแปรจ่ายออกจริง → ต้องมี quota เสมอ (บทเรียนเดียวกับ ASR)

## ทางเลือกที่ไม่เอา

| ทางเลือก | เหตุผลที่ไม่เอา |
|---|---|
| ต่อบอตภายนอก (Dialogflow/Rasa) อย่างเดียว | ขายไม่ได้ในฐานะโมดูล และ handoff/บริบท/QM ขาดตอน |
| ให้บอตเป็นเจ้าของช่องทาง (แยกจาก flow) | ได้ routing สองชุด อธิบายเส้นทางงานไม่ได้ |
| บอตตอบอิสระจากความรู้ทั่วไปของโมเดล | ตอบผิดโดยฟังดูน่าเชื่อ — ความเสียหายกับแบรนด์เกินคุ้ม |
| ฝึก/โฮสต์โมเดลเอง | พาภาษาที่สาม + GPU เข้ามาโดยไม่ได้เพิ่มมูลค่าที่ลูกค้าจ่าย |
| KB แยกกันระหว่างบอตกับ agent | คำตอบไม่ตรงกัน ซึ่งแย่กว่าไม่มีคำตอบ |
