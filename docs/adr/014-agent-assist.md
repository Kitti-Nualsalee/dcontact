# ADR 014: Agent Assist — เริ่มที่ "สรุปหลังจบสาย" ไม่ใช่ "ช่วยระหว่างสาย" และคำแนะนำทุกอันต้องกดปฏิเสธได้

- **สถานะ:** Accepted
- **วันที่:** 2026-08-08

## บริบท

Agent assist คือสิ่งที่คู่แข่งใช้เป็นหัวหอกการขายปี 2024–2026
(Zoom = AI Expert Assist, NICE = Enlighten Copilot / RTIG)
แต่มันเป็นโมดูลที่ **ทำพลาดง่ายที่สุด** เพราะอยู่บนหน้าจอ agent ตอนกำลังคุยกับลูกค้า —
ถ้าช้า ผิด หรือรก มันไม่ใช่แค่ไม่ช่วย มันทำให้สายเสีย

ของที่มีอยู่แล้ว: transcript pipeline + category DSL ([ADR-010](010-quality-management.md)),
KB + retriever ([ADR-013](013-virtual-agent-knowledge.md)), workspace ของ agent

## การตัดสินใจ

1. **ลำดับคือ after-call → during-call ไม่ใช่ทางกลับ**
   ทำ **auto wrap-up summary** ก่อน: ใช้ transcript ที่มีอยู่แล้ว, ไม่ต้อง streaming ASR,
   วัดผลได้ตรง ๆ ด้วย ACW ที่ลดลง, และผิดพลาดได้โดยไม่มีลูกค้าอยู่ในสาย
   real-time guidance ต้องรอ streaming ASR ภาษาไทยที่ latency ผ่านเกณฑ์
   ([quality-management §5](../quality-management.md) ระบุข้อจำกัดไว้แล้ว)

2. **`apps/assist` ไม่ใช่ service ใหม่ — เป็น role ของ `apps/qm`**
   ใช้ transcript pipeline, provider abstraction, evidence contract และ prompt registry ตัวเดียวกัน
   การตั้ง service ใหม่แปลว่าต้องมี ASR สองเส้นทางที่ให้ผลไม่ตรงกัน
   (ยกเว้นกรณี real-time ในเฟส A4 ที่ต้องมี worker แยกเพราะ latency budget คนละโลก)

3. **ทุกคำแนะนำต้องมีที่มา และกดปฏิเสธได้ในคลิกเดียว**
   สัญญาหลักฐานเดียวกับ auto-QM ([ADR-010](010-quality-management.md) ข้อ 9):
   การ์ดคำแนะนำต้องบอกว่ามาจากบทความไหน/ประโยคไหนในสาย
   การกดปฏิเสธถูกเก็บเป็นสัญญาณคุณภาพ — **อัตราการยอมรับคือ KPI ของโมดูลนี้**
   ถ้าต่ำกว่า 30% ให้ปิดฟีเจอร์นั้นทิ้ง ไม่ใช่ปรับ prompt ไปเรื่อย ๆ

4. **สรุปที่ AI ร่างเป็น DRAFT เสมอ — agent เป็นคนกดยืนยัน**
   หลักการเดียวกับคะแนน AI: มนุษย์เป็นผู้ตัดสิน สรุปที่ถูกแก้ไขถูกเก็บทั้งฉบับร่างและฉบับแก้
   (คือข้อมูลฝึกที่ดีที่สุดที่จะมี และเป็นหลักฐานว่าใครเขียนอะไร)

5. **ห้ามส่งข้อความหาลูกค้าโดยอัตโนมัติ**
   assist เสนอข้อความได้ แต่การกดส่งเป็นของ agent เท่านั้น (ทั้ง v1 และหลังจากนั้น)
   นี่คือเส้นที่ไม่ย้าย — ระบบที่พิมพ์แทนคนได้จะพิมพ์สิ่งที่ผิดแทนคนได้ด้วย

6. **Redaction ก่อนออกจากระบบ ไม่ใช่หลังกลับเข้ามา**
   prompt ที่ส่งออก provider ภายนอกต้องผ่านชั้นปกปิด PII (เลขบัตร, เลขบัญชี, เบอร์)
   ชั้นเดียวกับที่ [ADR-013](013-virtual-agent-knowledge.md) ใช้

7. **Latency budget เป็นข้อกำหนดของฟีเจอร์ ไม่ใช่ตัวเลขที่วัดทีหลัง**
   during-call: การ์ดต้องขึ้นภายใน **2.5 วินาที** หลังประโยคจบ ไม่งั้นบทสนทนาไปไกลแล้ว
   ถ้าทำไม่ได้ในภาษาไทย ให้ปล่อยเฉพาะ after-call — ไม่ปล่อยของช้าออกไปให้ agent ด่า

## ผลที่ตามมา

- `interactions` เพิ่ม `summary_draft`, `summary_final`, `summary_edited_by` (kernel change เล็ก)
- workspace ของ agent ได้แผงใหม่ด้านขวา (assist panel) — เปิด/ปิดได้ต่อ tenant และต่อคน
- prompt ทุกตัวอยู่ใน **prompt registry ที่มีเวอร์ชัน** ร่วมกับ auto-QM — เปลี่ยน prompt = เวอร์ชันใหม่
  และผลลัพธ์เก่าอ้างอิงเวอร์ชันที่ใช้ตอนนั้นได้เสมอ
- entitlement: `modules.assist.{enabled, autoSummary, knowledgeSuggest, realtimeGuidance}`
  + quota `assistSummariesPerMonth` (ต้นทุนผันแปรจ่ายออกจริง)

## ทางเลือกที่ไม่เอา

| ทางเลือก | เหตุผลที่ไม่เอา |
|---|---|
| ทำ real-time guidance ก่อน | ต้องมี streaming ASR ไทยที่ยังพิสูจน์ไม่ได้ + ผิดพลาดต่อหน้าลูกค้า |
| ให้ assist ส่งข้อความ/ตอบแทน agent อัตโนมัติ | ความเสียหายย้อนกลับไม่ได้ และทำลายความไว้ใจในตัวโมดูล |
| แยกเป็น `apps/assist` ตั้งแต่วันแรก | ASR สองเส้นทาง ผลไม่ตรงกัน ค่าดูแลสองเท่า |
| สรุปแล้วบันทึกเลยโดยไม่ให้ agent ยืนยัน | สรุปผิดกลายเป็นบันทึกทางการของบริษัท |
