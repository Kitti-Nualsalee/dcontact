# ADR 009: Plan & entitlement model — จุดบังคับใช้เดียว, ลดระดับแบบอ่านอย่างเดียว, on-prem ใช้ไฟล์ license เซ็นชื่อ

- **สถานะ:** Accepted
- **วันที่:** 2026-08-07

## บริบท

[multi-tenancy §5](../multi-tenancy.md) ระบุไว้แล้วว่า plan กำหนดเพดาน (seats, voice minutes,
WA conversations, storage) และ enforcement อยู่ที่ kernel แต่ยังไม่มี model จริง —
มีแค่ตัวเลขใน mockup

[ADR-008](008-workforce-management.md) เพิ่ม **WFM** เป็นโมดูลแรกที่ต้องขายแยกจากแกนหลัก
(หน้าเว็บขายกำหนดว่า WFM เริ่มที่แพ็กเกจ Growth) จึงเป็นจุดที่บังคับให้ต้องมีระบบ
entitlement จริง ไม่ใช่แค่ quota

ข้อจำกัดที่กำหนดการออกแบบ:

1. **มีสองโลกที่ต่างกันสิ้นเชิง** — SaaS (เราคุมเครื่อง) กับ on-prem ตาม [ADR-006](006-multi-vendor-telephony-gateway.md)
   (ลูกค้าคุมเครื่องและเข้า Postgres ตัวเองได้)
2. **คอนแทคเซ็นเตอร์หยุดไม่ได้** — การหมดอายุของ license ต้องไม่ทำให้รับสายไม่ได้
3. WFM จะไม่ใช่โมดูลสุดท้ายที่ขายแยก — โครงต้องรับโมดูลที่ 2, 3 โดยไม่ต้องแก้ที่เดิมซ้ำ

## การตัดสินใจ

1. **แยก "entitlement" ออกจาก "quota" เป็นคนละแนวคิด**
   - **entitlement** = *ได้รับอนุญาตให้ใช้อะไร* (โมดูลเปิด/ปิด, เพดาน seat ของโมดูล) —
     เปลี่ยนตอนซื้อ/อัปเกรด ตรวจแบบ synchronous ก่อนทำงาน
   - **quota** = *ใช้ไปเท่าไรแล้ว* (นาทีโทร, WA conversations, storage) —
     วัดจาก `dc.interaction.events` แบบ asynchronous, soft limit เตือน / hard limit บล็อกการสร้าง

   ทั้งสองอยู่ในโครงสร้างเดียวกันแต่คนละ key และคนละกลไก — รวมกันเมื่อไรจะสับสนทันที
   ว่าตัวเลขที่เห็นคือสิทธิ์หรือการใช้จริง

2. **entitlement เป็น tenant metadata ตาม [ADR-005](005-multitenant-metadata-architecture.md)** —
   เก็บใน Postgres, cache ใน Redis, invalidate ผ่าน `dc.tenant.events` ที่มีอยู่แล้ว
   **ไม่เพิ่ม topic ใหม่**

3. **ค่าที่ใช้จริงมาจาก 3 ชั้น และไม่ใช่ "min ทั้งหมด"**

   ```
   plan (ค่าตั้งต้นตามแพ็กเกจ)
     ← tenant override (sales เปิด trial/ต่อรองรายลูกค้าได้ — เพิ่มหรือลดก็ได้ ต้องมี audit + วันหมดอายุ)
     ← license ceiling (เฉพาะ on-prem — เป็นเพดานเสมอ ใช้ min)
   ```

   `effective = clamp(override ?? plan, ceiling = license)` — override **เพิ่มสิทธิ์เกิน plan ได้**
   (ไม่งั้นทีมขายทำงานไม่ได้) แต่ **เกิน license ไม่ได้** บนเครื่องลูกค้า

4. **จุดบังคับใช้ต้องเป็นจุดเดียวในโค้ด — ห้าม `if (hasWfm)` กระจาย** ใช้ NestJS guard
   ผ่าน decorator `@RequiresEntitlement('wfm.autoSchedule')` ครอบที่ controller
   ถ้ากระจายเช็กเอง วันที่เพิ่มโมดูลที่สองจะหาไม่เจอว่าต้องแก้ตรงไหนบ้าง

5. **แต่จุดตรวจต้องมี 2 ด่าน** — ด่านที่สองอยู่ที่ **ขอบของ job**: `apps/wfm` ตรวจก่อน
   publish เข้า `dc.wfm.jobs` และ **`apps/wfm-engine` ตรวจ claim ที่ติดมากับ job ซ้ำอีกครั้ง
   ก่อนเริ่ม solve** เพราะ engine คือตัวที่กิน CPU จริง ถ้าด่านแรกพลาดหรือมีใครยิง Kafka
   ตรงได้ ด่านแรกไม่ช่วยอะไรเลย

6. **การซ่อนเมนูใน UI คือ UX ไม่ใช่ enforcement** — ต้องทำทั้งคู่ แต่ห้ามพึ่งอย่างหลัง
   และเมนูที่ล็อกให้ **แสดงว่ามีอยู่แต่ล็อก** ไม่ใช่ซ่อนหาย (ลูกค้าต้องรู้ว่ามีของให้ซื้อ)

7. **ไม่ยัด entitlement ลง JWT** — access token อายุ 10 นาที ([iam-architecture](../iam-architecture.md))
   แปลว่าลูกค้าจ่ายเงินอัปเกรดแล้วยังใช้ไม่ได้อีก 10 นาที และเวลา debug จะแยกไม่ออกว่า
   สิทธิ์ที่เห็นมาจาก token เก่าหรือของจริง token ถือแค่ tenant + role เหมือนเดิม
   entitlement อ่านจาก config cache ฝั่ง server

8. **error ของการไม่มีสิทธิ์ต้องมี machine-readable contract** ไม่ใช่ 403 เปล่า:
   ```json
   { "error": "ENTITLEMENT_REQUIRED", "entitlement": "wfm.autoSchedule",
     "currentPlan": "starter", "requiredPlan": "growth" }
   ```
   เพื่อให้ UI ขึ้นหน้าชวนอัปเกรดที่ตรงเรื่องได้ แทนที่จะขึ้น "เกิดข้อผิดพลาด"

9. **on-prem ใช้ไฟล์ license แบบเซ็นด้วย Ed25519 ตรวจแบบออฟไลน์** ฝัง public key ไว้ใน image
   ไม่ phone home (on-prem บางที่ตัดเน็ตจริง) — และ**ยอมรับตั้งแต่ต้นว่านี่คือการป้องปราม
   ไม่ใช่การป้องกัน** ลูกค้าที่ตั้งใจโกงแก้ฐานข้อมูลตัวเองได้เสมอ สิ่งที่ระบบต้องทำคือ
   **ทำให้การละเมิดเป็นการจงใจที่พิสูจน์ได้ในชั้นสัญญา** และเก็บ **seat สูงสุดรายเดือน**
   ไว้ให้ export — ตัวเลขนี้มีค่าตอนต่อสัญญามากกว่าการพยายามล็อกซอฟต์แวร์

10. **license หมดอายุห้ามกระทบการรับสายเด็ดขาด** ลดระดับเป็นขั้นแทน:
    ```
    ACTIVE → EXPIRING (เตือน 30 วันก่อน) → GRACE (30 วัน, อ่านอย่างเดียว) → LOCKED
    ```
    LOCKED = สร้าง/แก้ของใหม่ไม่ได้ แต่ **ยังดูข้อมูลเดิมได้ตลอด** และ
    **router/telephony ไม่ผูกกับ license เลย** — สอดคล้องกับ ADR-008 ข้อ 3 ที่ตารางกะ
    เป็น soft constraint อยู่แล้ว router จึงไม่รู้จัก WFM ตั้งแต่ต้น

11. **ห้ามลบข้อมูลตอนดาวน์เกรดหรือหมดอายุ** ตารางกะล่วงหน้าสองเดือนหายเพราะบัตรเครดิตหมดอายุ
    คือความเสียหายที่กู้ความเชื่อมั่นไม่กลับ — ข้อมูลอยู่ต่อ แค่แก้ไม่ได้

12. **นับ seat ของโมดูลจากการที่ admin ติ๊กเปิดให้รายคน ไม่ใช่นับอัตโนมัติจากการใช้งาน** —
    บังคับเพดานตอนติ๊ก การนับอัตโนมัติจากคนที่มีชื่อในตารางกะทำให้ลูกค้าเจอบิลเกิน
    โดยไม่รู้ตัว ซึ่งเป็นสาเหตุอันดับต้น ๆ ของการยกเลิกบริการ

13. **ตั้งชื่อแพ็กเกจชุดเดียวทั้งระบบ: `starter` / `growth` / `enterprise`** —
    ก่อนหน้านี้ `platform.html` ใช้ Starter/Business/Pro แต่หน้าเว็บขายใช้
    Starter/Growth/Enterprise ต้องเลือกชุดเดียวก่อนผูกกับ entitlement
    ไม่งั้นตารางสิทธิ์จะอ้างชื่อที่ไม่มีอยู่จริง (ยึดตามหน้าที่ลูกค้าเห็น)

14. **`wfm.autoSchedule` แยกเป็น key ของตัวเอง แม้ตอนนี้จะให้มาพร้อม Growth** —
    CP-SAT ใน `apps/wfm-engine` คือต้นทุน compute จริงและเป็นสิ่งเดียวใน WFM ที่แพงตามการใช้
    วันที่ต้องแยกขายจะทำได้ด้วยการเปลี่ยนค่าใน plan ไม่ใช่แก้ schema หรือโค้ด

รายละเอียด JSON schema, ตารางสิทธิ์ต่อแพ็กเกจ, รูปแบบไฟล์ license, และ state machine
ของการหมดอายุ อยู่ใน [`docs/licensing.md`](../licensing.md)

## ผลที่ตามมา

- (+) เพิ่มโมดูลที่ขายแยกตัวถัดไป = เพิ่ม key ใน JSON + ติด decorator ไม่ต้องแก้กลไก
- (+) ใช้ `dc.tenant.events` + config cache เดิม — ไม่มี topic ใหม่ ไม่มี service ใหม่
- (+) การลดระดับแบบอ่านอย่างเดียวทำให้ **การหมดอายุไม่เคยเป็นเหตุการณ์ระดับวิกฤต**
  ทีมขายมีเวลาตามเก็บเงินโดยไม่ต้องเอาธุรกิจลูกค้าเป็นตัวประกัน
- (+) error contract ที่อ่านด้วยเครื่องได้ทำให้หน้าจอชวนอัปเกรดกลายเป็นช่องทางขาย
  ไม่ใช่หน้าจอ error
- (−) **override ต่อ tenant คือหนี้ที่สะสมได้** — ถ้าใช้พร่ำเพรื่อจะไม่มีใครรู้ว่าลูกค้ารายไหน
  ได้อะไรไปบ้าง → บังคับให้ทุก override มี `reason` + `expiresAt` + audit และมีหน้าที่ดู
  override ทั้งหมดในที่เดียว
- (−) **on-prem license ป้องกันจริงไม่ได้** — ต้องสื่อสารกับฝ่ายขาย/ผู้บริหารให้ตรงกัน
  ว่าเป็นเครื่องมือทางสัญญา ไม่ใช่ DRM มิฉะนั้นจะมีการลงทุนกับ obfuscation ที่ไม่คุ้ม
- (−) นาฬิกาบนเครื่องลูกค้าปรับย้อนหลังได้ → คุมได้แค่ `last_seen_at` แบบขยับขึ้นอย่างเดียว
  จับได้ว่าผิดปกติแต่ห้ามไม่ได้
- (−) ต้องมี **การทดสอบเส้นทาง "ไม่มีสิทธิ์" ทุกโมดูล** ใน CI ไม่งั้นจะรู้ตัวว่ารั่ว
  ตอนลูกค้าใช้ฟีเจอร์ที่ไม่ได้จ่ายเงินไปแล้ว
- (−) การเปลี่ยนชื่อแพ็กเกจ (ข้อ 13) ต้องแก้ `platform.html` และ `admin.html` ที่มีอยู่เดิม
